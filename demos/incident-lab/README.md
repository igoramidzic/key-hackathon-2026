# Relay incident simulation lab

A local TypeScript demo environment for an incident-management agent. It provides six linked, browser-accessible mock services and a shared HTTP/SSE API. Every application, person, log, deployment, and chat message is synthetic. It requires no credentials or external integrations.

## Run

Requires Node.js 22+ and npm.

```sh
cd demos/incident-lab
npm ci
npm run dev
```

Open **http://127.0.0.1:4310**. The development frontend runs on port 4310 and proxies `/api` to the simulator on port 4311. All tabs share one in-memory simulation. Restarting the server resets its data.

For a production build served by a single process:

```sh
npm run build
npm start
```

Open **http://127.0.0.1:4311**. Set `PORT` to change the production server port. The server binds to loopback.

## Present the demo

1. Open the **Control** tab. Background telemetry is already streaming from 240 applications across 24 domains.
2. Select **Database exhaustion**, **Faulty deployment**, or **Latency cascade** and a target application. `checkout-api` is the default.
3. Click **Start incident**. At normal speed, detection occurs at 5 seconds, ownership lookup at 10, Teams collaboration at 16, and a proposed mitigation at 22. Use the dark demo bar at the top to switch tools and pause, resume, or accelerate the simulation to 2×/4×.
4. Open **Microsoft Teams**. The response room includes the service's on-call engineer and owner, a reliability engineer, and an incident commander. The scripted agent summarizes the incident and links to filtered evidence. **Simulate recovery** sits in the chat header.
5. Follow those links into GCP Logs Explorer, Kibana Discover, Moogsoft Situation Room, the ServiceNow CMDB/change record, and the Confluence runbook. Expand log entries to inspect trace IDs and metadata. Related fault logs share trace IDs.
6. Ask the agent about ownership, evidence, status, or mitigation. Replies are deterministic and scenario-aware, not generated by an LLM.
7. Click **Simulate recovery** in Teams or on the Control tab. Recovery telemetry, chat, service health, and the incident timeline update together. Inject another scenario or use **Reset simulation** for a clean run.

You can open each mock service in a separate tab. Live updates propagate through the same server-sent event stream. Provider interfaces are recognizable approximations, not exact replicas of current vendor products.

## Mock API

The following endpoints are available on either development port and on the production port. Responses are JSON except `/api/stream`.

| Method | Path                       | Purpose                                                           |
| ------ | -------------------------- | ----------------------------------------------------------------- |
| GET    | `/api/health`              | Readiness and synthetic-data indicator                            |
| GET    | `/api/state`               | Complete current simulation snapshot                              |
| GET    | `/api/stream`              | SSE `state` events every second and after mutations               |
| GET    | `/api/apps`                | All 240 application records                                       |
| GET    | `/api/logs`                | Logs; filter by `source`, `appId`, `severity`, `id`, `q`, `limit` |
| GET    | `/api/incidents`           | Recent incidents and evidence references                          |
| GET    | `/api/teams/messages`      | Current incident's conversation                                   |
| GET    | `/api/servicenow/cmdb`     | Ownership, contacts, dependencies, and changes                    |
| GET    | `/api/confluence/runbooks` | Scenario-specific runbooks                                        |
| POST   | `/api/control`             | `start`, `pause`, `reset`, `inject`, `resolve`, or `speed`        |
| POST   | `/api/messages`            | Submit `{ "text": "Who owns this app?" }` to the mock room        |

Inject a failure:

```sh
curl http://127.0.0.1:4311/api/control \
  -H 'Content-Type: application/json' \
  -d '{"action":"inject","scenario":"db-pool","appId":"checkout-api"}'
```

Consume the stream:

```ts
const events = new EventSource('/api/stream');
events.addEventListener('state', (event) => {
  const state = JSON.parse(event.data);
  console.log(state.simulation.phase, state.logs);
});
```

Set speed with `{ "action": "speed", "speed": 4 }`. Scenario identifiers are `db-pool`, `bad-deploy`, and `latency`. Invalid actions, unknown apps/scenarios, malformed JSON, oversized request bodies, and cross-origin mutations are rejected. You can inject another failure after recovery; reset clears the history.

The APIs are lightweight mock adapters, not implementations of each vendor's complete API. An actual agent can read these sources and post into the mock room, but this version automatically performs a scripted response workflow; replacing that orchestration is the next integration point.

## Architecture and extension points

- `types.ts`: shared, strict TypeScript contracts for applications, logs, incidents, messages, controls, and frontend adapters.
- `simulation.ts`: seeded fleet, synthetic log generation, scenario definitions, and incident state machine. Injected clocks make timing tests deterministic. Add scenarios to `SCENARIOS` and extend the corresponding shared type and runbook presentation.
- `server.ts`: Node HTTP server, input validation, SSE fan-out, read-only service adapters, and production asset serving.
- `public/app.ts`: routing, shared navigation, demo controls, and live-state rendering. Preserves search drafts, open log details, and chat scroll position across updates.
- `public/views/services.ts`: vendor-inspired log, correlation, ownership, deployment, and knowledge views.
- `public/views/teams.ts`: incident chat, participants, evidence cards, suggested questions, and recovery control.
- `vite.config.ts`: frontend build and development API proxy.

The simulation keeps a rolling buffer of 300 logs and the latest 20 incidents. Evidence attached to retained incidents is kept within that buffer; other log permalinks can expire as the stream advances. New incident injection starts a fresh chat. All data is process-local and intentionally ephemeral. There is no persistence, authentication, real alert detection, actual Teams messaging, or production remediation.

## Cloudflare deployment

Live demo: https://hackathon-incident-lab.kualia.workers.dev

The hosted version uses a Worker for the app and API, static assets for the interface, and a SQLite-backed Durable Object for each demo room. The existing Node server remains available for local development.

```sh
npm run build:cloud
npm run deploy
```

`cf` uses your locally authenticated Cloudflare account. Configuration is in `cloudflare.config.ts`. The Cloudflare Vite plugin generates runtime types during the cloud build; `tsconfig.worker.json` checks those separately from browser/Node types. `npm run dev:cloud` runs the Worker locally on port 8787.

Each browser receives a seven-day room cookie. Tabs in that browser share a simulation; separate browsers get independent rooms. To share a presentation, choose a random UUID v4 and send everyone `https://hackathon-incident-lab.kualia.workers.dev/?room=YOUR-UUID`. That URL selects the shared room for subsequent service links. Anyone with that room link can control its synthetic incident and read its mock chat; it is a demo capability link, not authenticated access. The site is publicly accessible and contains only synthetic data.

Controls and incident transitions persist immediately. Ordinary telemetry checkpoints every five seconds. The hosted simulation advances only while at least one live stream is connected, avoiding perpetual background work. Closing all viewers freezes simulated time; reopening resumes it. Rooms support up to 20 simultaneous stream viewers. Cloudflare resource usage is billed or limited according to the account plan.
